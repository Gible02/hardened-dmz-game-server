# 05 — Cisco ASA 5515-X (Firewall)

Config: [`../configs/asa-5515x.sanitized.txt`](../configs/asa-5515x.sanitized.txt)
Status: **deployed and verified** — last touched 2026-09-14

## Role

The control point of the whole design. Three zones on three physical interfaces, with the
game host isolated on its own leg.

| Interface | nameif | Security level | Address |
|---|---|---|---|
| Gi0/0 | inside | 100 | 192.168.10.1/24 |
| Gi0/2 | dmz | 50 | `<DMZ_IF_IP>` — read back and fill |
| Gi0/3 | outside | 0 | 192.168.100.2/30 |

## This firewall performs no NAT

`show nat` returns empty, and that is correct. The ASA routes and filters between private
subnets; the 1921 owns every translation. Two consequences follow:

- The 1921's inbound static NAT must target 192.168.20.10, not this device's outside interface.
- `OUTSIDE-IN` line 1 expects a destination that is already the real host.

## Platform quirks on this unit

- **Gi0/1 is physically faulty.** No link with correct config on both ends and a known-good
  cable. Outside was relocated to Gi0/3. Full diagnosis in [`14-troubleshooting-log.md`](14-troubleshooting-log.md).
- **No expansion module.** Only Gi0/0–Gi0/5 exist; there is no Gi1/x. Confirmed with
  `show interface ip brief` and `show module`.
- **Arrived with residual configuration** despite appearing factory-default — a stray ACL entry
  referencing a WireGuard-style `192.168.10.10:51820`. Resolved with `write erase` + `reload`
  and a rebuild from a verified clean state.
- ASA 9.3(3), 8192 MB RAM, Clarkdale 3059 MHz, serial FCH200571EJ.

## Access lists as deployed

**`OUTSIDE-IN`** — five elements, applied inbound on outside:

| Line | Rule | Purpose |
|---|---|---|
| 1 | `permit udp any object MC-SERVER eq 19132` | The single exposed service |
| 2 | `permit icmp any any echo-reply` | Return path for outbound pings |
| 3 | `permit icmp any any unreachable` | Path MTU discovery |
| 4 | `permit icmp any any time-exceeded` | Traceroute sanity |
| 5 | `deny ip any any log informational` | **C-04** — explicit, logged deny |

Line 5 matters more than it looks. The implicit deny is silent; an explicit logged deny turns
every scan and probe into a record you can read.

**`DMZ-IN`** — two elements, applied inbound on dmz:

| Line | Rule | Purpose |
|---|---|---|
| 1 | `deny ip object DMZ-NET object INSIDE-NET log informational` | **C-02** — containment |
| 2 | `permit ip object DMZ-NET any` | Outbound internet access |

**C-02 is the control that matters most.** If the game server is compromised — via an
application RCE like Log4Shell, a malicious mod, or a stolen credential — the attacker's next
move is to enumerate and pivot into the trusted LAN. That packet hits line 1, is dropped, and
is logged with source and destination. The attacker is contained to a segment holding one
machine and no data worth taking.

**Known gap on line 2.** `permit ip DMZ-NET any` means egress is currently unrestricted. The
default-deny egress control (C-03) is not yet implemented. See the README gap note.

## Security levels vs ACLs

Security levels (100 / 50 / 0) set the default direction of trust: by default, higher may
initiate to lower and not the reverse. They do **not** enforce the policy in this build — the
ACLs do, and both interfaces have one applied inbound. Relying on security levels alone would
leave the DMZ able to initiate into nothing but would not produce a log entry when it tried.
